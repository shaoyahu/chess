# 视觉设计系统 v2 —— 「纸与墨」Paper & Ink

> 目标：把「能用的棋局页面」变成「愿意一直开着的棋局页面」。
> 出发点：用户反馈「目前不是很好看，而且有很多地方还使用的浏览器原生控件样式」。
> 本文件是**实现的依据**，不是事后补的说明书 —— 下面的 token 值就是代码里的值。

---

## 0. 先自我批判（避免又做成一个「通用默认」）

旧站的实际观感是：暖米色底（`#f2efe9`）+ 赭石主色（`#8f6209`）+ 系统默认无衬线 + 一堆圆角白卡片。

这正好是 AI 生成界面的**默认三件套**（暖米 + 高对比衬线 + 赭石），问题不在于它难看，
而在于它**没有信息量** —— 换成任何别的产品都长得一样，跟「棋」没关系。

所以这一版刻意做三件事：

1. **底色从暖米换成冷纸灰**：把"咖啡馆"换成"图纸 / 记谱纸"。
2. **主色从赭石换成靛蓝**：冷色更像仪器，暖色留给棋盘木纹，两者不打架。
3. **不用衬线体做正文**：中文衬线在小字号下发虚，正文一律黑体族；衬线感改由
   「等宽数字 + 细刻线」的排版细节承担。

**另一个自我批判**：第一版草案里我在大厅做了「居中 Hero 大卡片 + 渐变背景」，
写完自己念了一遍 —— 这是 SaaS 落地页模板，不是棋类工具。推翻。
大厅最终是**工作台**形态：左「开始一局」右「房间列表」，一屏能干活，不需要滚动。

## 1. 色彩 token（核心 6 色 + 2 档主色深浅）

| token | 值 | 角色 | 用在哪 |
|---|---|---|---|
| `--paper` | `#eef1f6` | 页面底（冷纸） | body 背景 |
| `--card` | `#ffffff` | 面板 | 卡片 / 弹层 / HUD |
| `--sink` | `#e6ebf3` | 凹陷面 | 次级按钮、输入框、表格行 |
| `--ink` | `#131c26` | 主文字 | 标题、正文 |
| `--ink-2` | `#46566b` | 次要文字 | 说明、副标题 |
| `--ink-3` | `#5f6f83` | 辅助文字 | 计数、时间戳、占位符 |
| `--indigo` | `#2f5ea8` | 主色（交互） | 强调按钮、选中态、落子权标记 |
| `--indigo-deep` | `#234a86` | 主色深（承载白字） | 主按钮底、开关滑块 |
| `--vermilion` | `#b4341f` | 危险 / 错误 | 认输、错误卡片、低棋钟 |
| `--jade` | `#0f6f5c` | 成功 / 在线 | 在线状态、成功提示 |

**语义纪律**：

- 主色（靛蓝）= 「你可以点的、当前生效的」。
- 朱砂 = 「会结束对局的、要小心的」，**只**用于危险与错误，不做装饰。
- 青玉 = 「连接正常 / 成功」。
- 琥珀 `#d9930d` = 棋盘上「上一步」的箭头（唯一一个第四色，与木色棋盘呼应）。
- **靛蓝半透明** = 棋盘上「建议着法」的箭头（与主色同族 = 系统给你的建议）。

所有正文级组合按 WCAG AA（≥ 4.5:1）核过，`npm run contrast` 是硬门禁。

## 2. 字族角色（2 个字族，3 个角色）

| 角色 | 字族 | 用在哪 |
|---|---|---|
| 正文 / 标题 | `--font-sans`：PingFang SC → Hiragino Sans GB → Microsoft YaHei → system-ui | 所有中文 |
| 数据 / 编号 | `--font-mono`：ui-monospace → SF Mono → Menlo | 房间码、棋钟、回合数、坐标、eyebrow |

三个排版角色：

- **eyebrow**：英文全大写 mono，10px，字距 `0.18em`，`--ink-3`。
  用作 section 的「小标题」，只出现在 section 头部。
- **title**：中文 15px / 600 字重，字距 `-0.01em`。
- **meta**：mono 11px，`font-variant-numeric: tabular-nums`，配 `--ink-3`。
  用来放计数（房间数、步数、在线人数）—— 数字对齐是「仪器感」的主要来源。

数字（棋钟、回合、计数）一律 `tabular-nums`，跳动时不左右抖。

## 3. 间距 / 字号 / 圆角：可调

三个**连续维度**暴露成 CSS 变量，用户在设置里用滑块调（不是分段按钮）：

```
--ui-scale   0.90 ~ 1.20   字号倍率
--ui-density 0.85 ~ 1.15   间距密度倍率
--ui-radius  4 ~ 18 px     圆角
```

派生：

```
--fs-xs/sm/md/lg/xl  = calc(<基准> * var(--ui-scale))
--sp-1..--sp-6       = calc(<基准> * var(--ui-density))
--radius             = var(--ui-radius)
```

偏好存在 **localStorage**（个人偏好，不上服务端），由 `<html>` 上的内联变量应用，
刷新即生效。棋盘与引擎配置属于「系统配置」，仍走服务端 / 房间属性，两层不混。

## 4. 布局概念

三断点（与 skill 约定一致）：

| 断点 | 宽度 | 布局 |
|---|---|---|
| narrow | < 900px | 单列：HUD 在棋盘上、聊天在下；棋盘缩小 |
| medium | 900 ~ 1199px | 单列 + 更宽的间距；HUD 两列排布 |
| wide | ≥ 1200px | 三列：HUD 左、棋盘中、聊天右 |

对局页的**宽 / 窄**判定另有 JavaScript 逻辑（`planStageLayout`）：它看的是
「视口形状 + 分列后棋盘能不能变大」，而不是单纯断点 —— 正方形视口也按窄屏处理
（用户此前明确要求）。CSS 断点只管**间距与密度**，不动布局归属，避免两套逻辑打架。


## 4.1 页面上不写解释性文字（用户 2026-11-12 拍板）

**说明一旦印在界面上，界面就等于没设计好。**

所以大厅页现在**一句说明都不写**：

| 以前 | 现在 |
| --- | --- |
| 登录卡片的一段开场白 | 只剩「用户名 + 进入大厅」 |
| 每种开局方式下面的一句说明 | 没有 —— 字段名自己说得清 |
| 没选方式时那块闲置的说明面板 | 没有 —— 四枚带图标的按钮自己就是说明 |
| 底部整块「玩法说明」（6 条） | 整块删掉 |
| 名单底部「右键某个人 → 可以给他发消息」 | 行尾那枚**气泡按钮** |

留下的文字都是**状态**不是说明：在线人数、队列人数与时限、房间列表的空状态。

「怎么发消息」这种交互说明，改由**图标**承担 ——
名单行尾那枚气泡按钮就是说明书（点一下就进那个人的私信）。

## 5. 签名元素（全站只此一处）

**「落子权标记」**：一枚 **靛蓝实心方块 + 一条 3px 靛蓝竖条**，贴在
**当前该走棋的那一方**的玩家行左侧。

- 它不是「高亮边框」——边框高亮在整站到处都在用，不构成签名。
- 方块 + 竖条的组合**只**在落子权标记处出现，别处复用就稀释了。
- 靛蓝 = 「当前生效 / 该你了」，与主色语义一致。
- 呼吸动效（1.6s，透明度 0.55↔1）只在 `prefers-reduced-motion: no-preference` 下启用；
  动效**不是**信息本身，去掉之后照样认得出。

棋盘上的两种箭头各有专属色，不与签名混用：
**琥珀实心 = 已经走过的上一步**，**靛蓝半透明 = 引擎建议的下一步**。

## 6. 控件规范（去原生化）

| 控件 | 做法 |
|---|---|
| `<select>` | `appearance: none` + 自绘 chevron（SVG 背景），完全接管边框/圆角/焦点环 |
| `<input type=range>` | `appearance: none`，自绘轨道 + 滑块（WebKit / Firefox 双写） |
| `<input type=checkbox>` | 视觉隐藏，自绘 `.switch` 轨道 + 圆钮 |
| `<input type=text>` | 自绘边框 / 聚焦环 / 占位符 |
| `<button>` | 统一 `.btn` 体系：primary / ghost / danger / small / icon |

**图标**：全部走 `lucide-react`（ISC 开源许可，已过许可证门禁）。
功能按钮里**不再出现任何字符图标**（原来的 `⚙ 💬 ♟ ♞ ⚪ ⚫ ⚡` 全部换成 SVG）。

**焦点**：所有可聚焦元素有 `:focus-visible` 可见焦点环（靛蓝 2px + 2px 偏移）。
鼠标点击不出现焦点环，键盘 Tab 一定出现。

**Toast**：右上角固定、宽 380px、鼠标悬停暂停计时、`danger` 类 8 秒、
**后端错因原样透出**（不做二次演绎）。

## 7. 响应式与可访问性

- 三个断点见上表；grid 一律 `minmax(0, 1fr)`，长文本子项一律 `min-width: 0`。
- 弹层 `max-width: 100%`，内容区自己 `overflow: auto`，不撑破视口。
- 工具栏拆成「标签行 + 操作行」两块（窄屏时先标签后操作），不挤成一行。
- `prefers-reduced-motion: reduce` 时关闭所有过渡与关键帧动画。
- 对比度：正文 ≥ 4.5:1（`npm run contrast` 门禁）；装饰性元素（棋盘坐标）守下限 2:1。

### 7.1 五条实现时踩过的铁律

**① flex 子项的默认 `min-width` 是 `auto`（= 它的 min-content 尺寸），不写 `0` 就压不下去。**

最容易漏的是**「装长内容的父级那一行」**：给里面的滚动容器写了 `min-width: 0`，
父级那一行的 automatic minimum size 仍然按内容算 —— 它挡不住。

> 本轮真事故：窄屏对局页的「快捷聊天 + 棋谱」那一行没写 `min-width: 0`，
> 这一行被撑到 425px，把 406px 宽的列顶破，430px 视口下整页横向溢出 83px。
> 修法是一行 CSS；**漏掉它的是「规则写了但实现时没逐条对照」**。

**② 「页面不横向溢出」必须逐页面量，不能拿一个页面推断另一个。**

大厅页（工作台）和对局页（舞台）的布局归属完全不同，
大厅不溢出**不代表**对局页不溢出。门禁要覆盖**每一个页面 × 关键宽度**，
窄屏必测 **390 / 430**（430 是真实手机宽度，最容易漏）。

**③ `flex-basis` 跟着容器的轴走 —— 同一个数字换个方向就是另一个意思。**

`.chat-input-row` 写着 `flex: 0 1 258px`，本来是给**横排**聊天带留的宽度。
改版把聊天区改成**竖排**之后，这 258px 就落到了**高度**上，
输入框被撑到 258px 高 —— 比整块聊天记录区还高。

> 数字没变、轴变了，含义就反了。
> 写 `flex: <数字>px` 之前先问一句：**这里的容器是 row 还是 column？**

**④ 门禁判据要在目标视口下「可能不成立」；要量真正决定结果的那个量。**

一条判据如果在该视口下**恒真**（永远成立）或**恒假**（永远不成立），
它就只是装饰品 —— 靠它抓变异等于抓空气。

> 本轮真事故：变异【二十一】连抓三次没抓到，查出来两条原因。
> ① **量错了地方**：棋盘尺寸其实由 CSS 的 `--board-vh` 决定，
>    JS 里那个 `STACK_EXTRA_H` 只参与宽/窄屏的**比较**、不决定尺寸。
>    ② **判据恒真 / 恒假**：`.page` 是 100vh 固定高度 →「页面出不出滚动条」恒假；
>    棋盘边长有 176px 下界 →「棋盘 ≥ 120px」恒真。
>
> 修法：加一条**对账式判据**（棋盘边长必须 = 视口高 − 估算值），
> 它对**任何方向**的估算偏差都敏感。

**⑤ 门禁分组要按「机制」分；共享的状态不许关进门禁块里。**

「跳过不属于本次分组的门禁」听起来只是少测几件事，实际上：
如果被跳过的块里带着**视口切换**或**对局状态变更**，后面所有块测到的页面状态就全变了，
门禁会**假红** —— 而且红得「很合理」，容易误判成新功能坏了。

所以分组的规矩是三条：

1. **按机制分，不按控件分。**「聊天」「战利品」「落子权」是机制；「按钮」「下拉框」是控件
   —— 按控件分会让一条变异跨好几组。
2. **共享的测量与准备代码必须「总是执行」。** 视口切换、2D/3D 切换、建房间这类
   有副作用的动作，要从门禁块里**提出来**放到块外面 —— 提的是「放哪」，
   不是「什么时候跑」，**顺序必须和原来一模一样**。
3. **一个块里的断言必须整体启用。** 包裹块的 `gateEnabledAny([...])` 要列全
   这个块里实际断言的门禁，不能只写块名。

> 本轮真事故：给 `verify-move-arrow.ts` 做分组时，把「建对手房间」留在了 3D 那个门禁块里。
> 结果「只跑聊天组」时对手根本没建起来，后面的求和/悔棋全红。
> 查出来才发现：**准备代码和门禁断言混在同一个块里**，跳过一个就把状态带偏了。

## 8. 聊天与弹幕

### 8.1 一条规则：所有聊天消息既进聊天窗口，又飘弹幕

打字的和点快捷按钮的**走同一条路**（服务端统一广播 `t: 'chat'`），
收到之后客户端做两件事：**写进聊天记录** + **飘一条弹幕**。

以前是两套（打字的只进记录 / 快捷的只飘弹幕），两边都只做了一半 ——
聊天框空空的，用户以为消息没发出去。两条路必然漏一边，统一成一条。

服务端把 `room.chat` 随房间快照一起广播，所以**后来进房的人也能看到之前的聊天**。

### 8.2 弹幕是「一眼看完」的媒介

| | 聊天记录 | 弹幕 |
|---|---|---|
| 名字 | 完整 | 最多 8 字 |
| 正文 | 完整（≤200 字） | 最多 20 字（超了加省略号） |
| 位置 | 右列 / 弹层 | 棋盘上方，4 条轨道 |
| 存活 | 永久留底 | 6 秒 |

弹幕从**右上方**飘向左方，不贴视口顶部 —— 贴顶部会从信息栏背后飘过去。

### 8.3 输入框的高度由内容说了算

聊天输入框是**单行**的（高 33px），不是一堵墙。
行高交给 `flex: 0 0 auto`（见 7.1 铁律③），**不要**再加
`align-self: center` 之类「让子项不跟着行高拉伸」的保险 ——
那会让行高异常这件事在界面上完全看不出来，门禁也就量不到问题。

## 9. 战利品（双方吃子）

### 9.1 归属：显示在**吃子方自己那一行**的下方

国际象棋的惯例：白方吃掉的黑子，记在**白方**名下；黑方吃掉的白子，记在**黑方**名下。

- 白方行下面 = 白方吃掉的**黑**子
- 黑方行下面 = 黑方吃掉的**白**子

**不要**把「谁被吃了的棋子」和「吃人的一行」分开摆 —— 那会让人多看一次才能对上是哪一方。

### 9.2 表示：小棋子图标，不用数量标记

用自产的 `PieceGlyph` SVG 缩到 **20px**，不是新画的素材：

- 2D / 3D 的造型语言一致（两边的 HUD 本来就是同一套组件）；
- 白棋在浅色底上要加 `drop-shadow` 才看得清轮廓（`.cap`）；
- 一眼能数出个数，不会把「后」和「兵」认混。

一行放不下 15 颗时换行（`flex-wrap: wrap`），战利品带与名字行左对齐（`padding-left: 11px`）。

### 9.3 2D / 3D 共用一套

对局页的 HUD 是**同一个组件**，所以战利品带只写一次，两边都有。
门禁 V18 因此只需要测一遍，然后切到 3D 再断言一次「还在」。

## 10. 提示该出现在哪儿

### 10.1 表单校验错误**常驻在字段旁边**

错在哪一行，就在那一行说清楚，而且**要一直在**（用户盯着输入框时它就该在）。

大厅的「房间码为 4 位字符」现在显示在输入框下方（`.field-error`，带 `role="alert"`，
输入框同时标 `aria-invalid`）。它**不是**一条 toast。

> 以前它走全局 toast：飘走、还跨页。toast 的语义是「刚刚发生的事」，
> 而**校验错误是「现在还没解决的事」** —— 飘走了用户就不知道该改哪儿。

### 10.2 toast 不跨页

toast 挂在**根布局**、状态在**模块级单例**里 —— 不处理的话，
大厅页的报错会一路跟着用户飘到对局页右上角，正好压在棋盘上方。

规则：**路由一变就把上一页的 toast 全收掉**（`ToastHost` 监听 `usePathname()`）。

副作用是「刚刚进房」时那些 toast（`房间已创建` / `已进入对局`）也会被清掉 ——
这是**对的**：人已经进房了，HUD 本身就在显示对局，不需要再被告知一次。

> 门禁要防「假绿」：那条 toast 8 秒后自己消失，所以 V21 先把它**悬停钉住**
> （toast 支持悬停暂停计时），钉住之后它只可能因为「换页被清掉」而消失。

### 10.3 用户主动打开的浮层 > 环境提示

在线名单浮层（`.online-panel`，z-index 520）和右键菜单（`.ctx-menu`，530）
都在 **toast 之上**（toast 是 500）。

原因：两者都在右上角，浮层从顶栏底下落下来、toast 也在顶栏底下 ——
不抬高的话，刚进对局页弹出的那条提示会把「在线 N 人」这行盖掉。

**用户主动打开的东西压过环境提示**：浮层是人在看的，toast 是自己冒出来的。

## 11. 弹窗的留白与裁切

设置弹窗（`.settings-panel`）是全站内容最长的弹层，也是唯一一个**会滚动**的。

### 11.1 留白写在滚动区里，裁切也会把留白裁掉

滚动区（`.settings-body`）的 `padding-bottom` 是**内容的一部分**：
内容放得下时它在最底下，放不下时它在**滚动区的末尾** —— 也就是**可视区之外**。

所以「加了内边距」和「看起来有内边距」是两件事：
一旦内容溢出，最后一项就会直接顶着面板下边缘，
**硬切**读起来像「被裁坏了」，而不是「还能往下滚」。

### 11.2 三条规则

1. **面板要够高**：`max-height: min(90vh, 780px)`。
   常见屏幕上内容整段放得下，底部留白自然看得见。
2. **四周都要留白**：头 `13px 18px`、体 `12px 18px 28px`，头与体左右对齐。
3. **放不下时用渐隐，不用硬切**：`.settings-panel::after` 是一层
   28px 高的 `linear-gradient(to bottom, transparent, var(--bg-panel))`。

### 11.3 渐隐层的高度**必须等于**底部留白

| 状态 | 渐隐层盖在什么上面 | 看上去 |
|---|---|---|
| 内容放得下 | 纯白的下留白 | 看不见 |
| 滚到底 | 还是纯白的下留白 | 看不见 |
| 下面还有内容 | 真实内容 | 渐隐 → 读得出「还有，往下滚」 |

两个数字对不上，就会出现「滚到底了底下还在发白」或者「留白被吃掉」。

**为什么不用 JS 监听 scroll**：渐隐层盖在哪里由**几何**决定，
不需要知道滚动状态 —— 少一个状态就少一处能出 bug 的地方。

> 门禁：V22 钉几何（留白 ≥ 16px、渐隐层在、方向朝下、高度 == 留白），
> V23 用**像素差分**钉「渐隐真的在挡东西」
> （把它 `display:none` 再截一张，两张不一样才算数）。
> CSSOM 全对 ≠ 渐隐在生效 —— 写成全透明时 CSSOM 一项都对，但一个像素都挡不住。
