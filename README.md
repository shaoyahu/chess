# ♞ 局域网国际象棋（LAN Chess）

一款在**同一个局域网**里多人实时对战的国际象棋网页游戏。

- **多人实时对战**：不同用户名进入大厅，两两配对即刻开局；第三人可以观战或自己开一局。
- **2D / 3D 双视角**：默认 2D，任意时刻可切换。对战双方视角**各自独立**——白方看到白棋在下，黑方看到黑棋在下，文件序相反。
- **规则由引擎裁决**：走子合法性、王车易位、吃过路兵、升变、将死/逼和/子力不足/三次重复等，全部由服务端权威校验。
- **素材全部自产**：棋子是本项目代码生成的几何图形与矢量图，木纹是程序化 Canvas 纹理，**没有任何第三方图片、字体或私有协议依赖**。
- **棋盘吃满空间**：2D 棋盘是**正方形**，边长吃满可用高度（宽屏 `100vh - 140px`、窄屏 `100vh - 294px`）；3D 棋盘的画布比例与透视投影一致，横向/纵向各占 **97%**，不留大片空白。
- **布局跟着屏幕走**：屏幕**宽**时 HUD 在棋盘**左边**、聊天在**右边**；屏幕**窄**（含正方形）时 HUD 在**上面**、聊天在**下面**。两种排法共用同一份页面结构，面板全在文档流里——**结构上就压不住棋盘**。走子记录不再占地方——棋盘上直接画**上一步**的走子箭头（2D 是棋盘箭头，3D 是贴棋面的立体箭头）。
- **明亮界面**：全站亮色主题，正文对比度均 ≥ 4.5:1；黑白棋子都带描边，落在深格或浅格上都认得出形状——3D 里黑棋也是**深身浅边**，不再糊成一团。
- **对局操作都在右侧浮层里**：认输**二次确认**，求和与悔棋是**同意 / 反对**两个按钮 + 30 秒倒计时（超时自动反对）。人机局不摆这两个按钮，只留一个**「撤回」**（可连点，一路撤回到开局）。提示是 `position: fixed` 的浮层，**不占文档流**——不会因为多一条提示文字就把页面顶出滚动条。

## 1. 快速开始

### 环境要求

- Node.js ≥ 18（开发使用 v22.23.2）
- 同一局域网内的其他设备（手机 / 平板 / 另一台电脑）

### 安装与启动

```bash
cd chess-game

npm install          # 安装依赖
npm run dev          # 开发模式（热更新），监听 0.0.0.0:3000
```

浏览器打开 <http://localhost:3000> 即可。

生产模式：

```bash
npm run build        # 生产构建
npm start            # 生产模式启动，仍监听 0.0.0.0:3000
```

### 查看局域网地址

```bash
npm run lan
```

会打印形如 `http://192.168.1.23:3000` 的地址，**其他设备用浏览器直接打开这个地址就能加入对局**——HTTP 与 WebSocket 共用同一个端口，不需要额外配置。

### 部署到云服务器

这个项目是**一个 Node 进程**（页面 + WebSocket 同端口，房间状态在进程内存里），不是静态站点。
要放到自己的云服务器 / VPS 上，**代码不用改**，照着 [`docs/deploy.md`](docs/deploy.md) 走即可：

```bash
npm ci && npm run build     # 构建（要带 devDependencies）
npm start                   # 起服务
npm run deploy:check        # 部署自检：HTTP / WebSocket / 引擎 / .data 可写 / 端口
```

`deploy/` 目录里备好了 systemd 单元、nginx 与 Caddy 的反代配置（**反代必须透传 WebSocket**，
否则表现是「页面能开、对局连不上」）。

> **尚未真的部署上去。** 球球决定先不部署。手册 [`docs/deploy.md`](docs/deploy.md) 的
> §14 / §15 记着一台共享生产机（`<ECS 公网 IP>`，已脱敏）的真实体检数据、以及一次证书修复的完整过程 ——
> 那台机器**不能在上面构建**（实测会拖垮另外 4 个线上站点），只能本地构建后传产物。

## 2. 局域网联机

### 四种开局方式

大厅左边的「开始一局」有**四个入口**，点开任意一种，下面的面板就换成这一种需要的东西
（**返回 + 字段 + 确定**）—— 每种方式要的字段不一样，摊在一张卡上只会让人以为「选了时间就能加别人的房」。

| 方式 | 面板里能选什么 | 说明 |
| --- | --- | --- |
| ⚡ 快速匹配 | 时限（多一个「任意」） | 进队列等对手。**只跟选了同一时限的人配对**；选「任意」则来者不拒 |
| 🤖 人机对弈 | 时限 + 难度 + **执子** | 立刻与内置 AI 开一局。**开局前可选「随机 / 我执白 / 我执黑」**（随机 = 服务端抽签，各 50%）。人机房间**不出现在房间列表里** |
| 🏠 创建房间 | 时限 + 房间类型 | 开一桌等人来。房间类型分**公开 / 邀请**（见下） |
| 🔑 加入房间 | 房间码 | 进别人开的房间。**时限由房主定**，这里不选时间 |

**房间类型**：

| 类型 | 别人怎么进来 | 大厅列表里 |
| --- | --- | --- |
| 公开 | 直接点「加入」入座 | 显示房间码 + 「加入」「观战」 |
| 邀请 | **只有拿到房间码的人**能加入 | **不显示房间码**，只有「观战」 |

观战：公开房、邀请房都能观 —— 在大厅的房间列表点「观战」即可。

### 房间列表

每一行显示：**谁 VS 谁**（只有一个人时只显示那个人的名字）、**时长**、**游戏状态**、
观战人数，以及房间类型标签（公开 / 邀请）。公开房还显示房间码，并且可以直接点「加入」进局。

**游戏状态**有五种：**等待对手** / **准备中** / **进行中** / **等待重连** / **已结束**。

只有一个人时，显示的是那位**「颜色待定」**的玩家 —— 他已经在房里等着了，
黑白要等对手到齐才抽（见下节），不是「空房间」。

### 防火墙

服务器监听 `0.0.0.0:3000`。如果其他设备打不开页面，多半是本机防火墙拦了 3000 端口。

**macOS**

```bash
# 查看系统防火墙状态
/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate
```

在「系统设置 → 网络 → 防火墙 → 选项」里允许 `node` 接受传入连接；或在终端临时放行：

```bash
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add /full/path/to/node --on
```

**Windows（管理员 PowerShell）**

```powershell
New-NetFirewallRule -DisplayName "LAN Chess 3000" -Direction Inbound -LocalPort 3000 -Protocol TCP -Action Allow
```

**Linux（ufw）**

```bash
sudo ufw allow 3000/tcp
```

其他检查：

- 确认两台设备在同一网段（不是手机流量 / 访客网络隔离）
- 路由器是否开启了「AP 隔离 / 客户端隔离」，开启后设备之间无法互通
- 换端口：`PORT=8080 npm run dev`

## 3. 玩法说明

### 黑白棋怎么定

**谁执白不由「谁先进来」决定** —— 是服务端**抽签**的结果。

| 场景 | 怎么定 |
| --- | --- |
| **人机对弈** | 开局前在面板里选：**随机** / **我执白** / **我执黑**。选「随机」= 服务端抽签，各 50% |
| **两个真人** | **两人到齐那一刻**由服务端抽签 —— 谁先到、谁后到都不影响结果 |
| **快速匹配** | 同上：两人配对时抽签 |

先进房的人不会直接坐定，而是进「**颜色待定**」状态（大厅和房间页都写着「待抽签」）。

真人局抽完签**不会立刻开局**，而是进入**准备**阶段：

1. 抽签结果当场揭晓 —— 房间状态栏写着「本局你执白 · 点「准备」开始」；
2. **双方都点「准备」才开局**，白方先走 —— 给抽到白方的人一点时间看清自己执的是哪一边；
3. 一方没点，就一直停在准备阶段，不会有人被先手偷袭。

重开一局（再来一局）会**重新抽签 + 重新准备**。

有人离开分两种后果：**开局前**离开 → 另一方退回「颜色待定」，等新对手来了重抽；
**对局中**离开 → 离开方判负，另一方**保留座位**、房间直接结束（这时候没有「换对手重抽」这回事）。

人机局**不走准备环节** —— 电脑不需要准备，点完直接开。所以对局中的状态栏会一直带着你的执色
（「你执黑 · 轮到你走」）。

### 落子

1. 点**自己**的棋子 → 棋盘高亮出全部合法落点（黑点是普通走法，红环是吃子）
2. 点高亮点 → 落子，走子记录与对端**实时同步**
3. 兵走到底线会弹出升变选择（后 / 车 / 象 / 马）
4. 不是你的回合时棋子不可选中

也可以**按住棋子拖**（见下）。

### 拖拽走子

除「点起点 + 点终点」外，还可以**按住棋子拖到目标格**。

> **点起点 + 点终点照常能用** —— 拖拽是**多加**的一条路，不是替换。
> 2D、3D 都是两套并存（门禁 D5 / D10 守着这条回归）。

| | 2D | 3D |
| --- | --- | --- |
| 按住棋子 | 棋子跟着指针走，**原格空出来** | 棋子**先抬起来一点**（Z 轴上抬约三分之一格），再跟着指针走 |
| 拖动过程中 | 显示落点提示（黑点 / 红环），**原格高亮** | 同左（棋面上的圆点 / 红环） |
| 松手 | 落在**棋子所在**的格子 | 同左 |
| 按住空白处 | （无操作） | **转视角**（拖拽旋转、滚轮缩放） |

几条规矩（2D / 3D **完全一致**）：

- **动了才算拖**：指针位移超过 4px 才算拖动；点一下仍然是「选中」—— 拖拽**不会**把原来的点选走子吃掉。
- **看到棋子在哪，就下到哪**：落点按**棋子**所在格判定，不是按光标所在格
  （抓着棋子边角拖时两者差着半格，按棋子判定才不会「看着在 A 格、却下到 B 格」）。
- **拖到不能下的地方 = 弹回原位**，不发出任何走子消息。
- 拖完之后**不会**顺手把棋子选中（浏览器在松手后还会补一次 click，那一下被吞掉）。

### 视角

- 右上角「2D / 3D」随时切换，**只影响你自己**，不影响对方
- 棋盘朝向由**你的执子颜色**决定：白方白棋在下，黑方黑棋在下
- 2D 走子为**平面位移**（棋子贴着棋面滑过去）
- 3D 走子为**立体位移**（棋子沿弧线抬离棋面再落下）
- 3D 里可**拖拽旋转**视角（有角度限幅，不会转到对面视角）、**滚轮缩放**
- 3D 旋转时**不自动缩放**：棋盘转过来就转过来，相机距离只由你的滚轮决定（代价：转到斜角时棋盘上下边缘会有一部分走出画布 —— 这是几何决定的）

### 棋盘有多大

棋盘边长由**视口的形状**决定 —— 页面会判断屏幕是「宽」还是「窄」，据此把 HUD 和聊天放到棋盘的**左右**或**上下**（判定规则见「对局页的布局」）。

| | 尺寸规则 |
| --- | --- |
| 2D · 宽屏 | 正方形，边长 = `100vh - 140px`（HUD / 聊天在两侧，不占纵向空间），且不超过中间那一列的宽度 |
| 2D · 窄屏 | 正方形，边长 = `100vh - 294px`（上下各让出 HUD 条 / 聊天块的位置） |
| 3D | 画布比例 = 棋盘透视投影的宽高比（1.5579），横向 / 纵向各占 97%。宽屏时高度按 `100vh - 140px` 算，窄屏时按 `100vh - 294px` 算 |

几个常见视口的实际尺寸：

| 视口 | 2D 排法 | 2D 棋盘 | 3D 排法 | 3D 画布 |
| --- | --- | --- | --- | --- |
| 1920×1080 | 宽（左右） | 940 × 940 | 窄（上下） | 1225 × 786 |
| 1600×1000 | 宽（左右） | 860 × 860 | 窄（上下） | 1100 × 706 |
| 1440×900 | 宽（左右） | 760 × 760 | 窄（上下） | 944 × 606 |
| 1280×800 | 宽（左右） | 640 × 640 | 窄（上下） | 788 × 506 |
| 1200×900 | 窄（上下） | 606 × 606 | 窄（上下） | 944 × 606 |
| 1000×1000（正方形） | 窄（上下） | 706 × 706 | 窄（上下） | 960 × 616 |
| 900×1200 | 窄（上下） | 860 × 860 | 窄（上下） | 860 × 552 |
| 430×932（手机竖屏） | 窄（上下） | 390 × 390 | 窄（上下） | 390 × 250 |

430px 这种手机宽度上，下面那一行是「💬 聊天」按钮 + 6 个快捷聊天 —— 放不下就**快捷聊天自己横向滚动**，页面本身不会横向溢出。

3D 的画布本身是**扁宽**的（1.56 : 1）：堆叠时它能吃满整行宽度，分列时却被中间那一列限死。所以 3D 在多数宽屏上反而走**窄屏**那一档 —— 例如 1920×1080 下堆叠是 1225×786，分列只有 1160×745。只有「又宽又矮」的视口（如 1600×900）3D 分列才划算。

3D 的取景不是手调的，而是**数值求解**出来的：按「棋盘 + 全部棋子（每个格子都可能站最高的王）」的最坏情况建模，解出相机距离 / 看向点 / 画布比例，保证任何局面、任何视角都不会把棋子裁掉。
`npm run solve:3d` 可以重新求解并打印推导过程。

### 看得清（配色）

全站是**亮色主题**：米白底 + 白色卡片，文字用近黑色（对比度 16.6:1），次要文字 7.3:1，最浅的一档辅助文字也有 4.7:1——都过了 WCAG AA 的 4.5:1 门槛。

棋子本身是**双色反衬**，这是「深底 / 浅底都认得出」的关键：

| | 棋身 | 描边 | 效果 |
| --- | --- | --- | --- |
| 白棋 | 米白 `#f6efe1` | 深褐 `#2f2519` | 落在深格上靠深边勾出轮廓 |
| 黑棋 | 深灰 `#3a3531` | 浅米 `#e6d9c3` | 落在浅格上靠浅边勾出轮廓 |

2D 用 SVG `stroke` 画描边，3D 用**反向外扩的轮廓壳**（沿法线外扩 0.017 个世界单位 + 背面渲染），保证透视和缩放下描边粗细一致、不会被高个子棋子的顶盖糊掉。

升变选择弹窗是白底，每个选项下面垫一层**迷你棋盘底纹**：白棋落在深格上、黑棋落在浅格上，两种颜色都不会和弹窗底色糊在一起。

3D 场景背景是冷灰蓝（`#cbd4de`），和暖色木纹在色相上分开，棋子轮廓在两种底色上都够清晰。

### 对局中可用的操作

| 操作 | 说明 |
| --- | --- |
| 认输 | **先弹右侧浮层二次确认**（「确认认输」/「取消」），确认后立即判负 |
| 提议和棋 | 对方在右侧浮层里「同意 / 反对」，**30 秒**不回应自动拒绝。**人机局没有这个按钮** |
| 悔棋 | **你刚走完、对方还没回应** → 点下去**直接撤回**你那一步（不用问对方）；**对方已经回应** → 点下去是**申请**，对方同意后撤**两步**（对方的应手 + 你那一步）、轮到你重走，**30 秒**不回应自动拒绝。你一步都没走过时按钮置灰。**人机局没有这个按钮** |
| 撤回 | **只给人机局**：单方面撤掉你上一步走的棋，**可以连点**，一路撤回到开局。见下节 |
| 再来一局 | 按钮显示在**自己那一行**（HUD 里没有全局按钮）：点过之后那一行变成「已申请」，**不能重复点**；对方申请了，他那一行也显示「已申请」。双方都申请后重置局面 |
| 聊天 | 房间内文字互通，观战者也能发言 |

### 求和 / 悔棋：右侧浮层，不是插在页面里的文字

以前「对方提议和棋」是**往棋盘上方插一条文字条**，消息一多就把页面顶出滚动条。现在这类提示统一改成**右侧浮层**：

- 浮层是 `position: fixed`，**不参与文档流** —— 弹出来也不会改变页面高度、不会顶出整页滚动条；
- 浮层里带**倒计时**（30 秒），到点服务端**自动拒绝**（客户端只负责显示倒计时，判断权在服务端）；
- 认输的二次确认也是同一个浮层（红色调），点「取消」什么都不会发生。

悔棋的语义（用户 2026-11-10 拍板、**2026-11-20 改**）：

| 局面 | 悔棋按钮 | 点下去发生什么 |
| --- | --- | --- |
| **A. 你刚走完、对方还没回应** | 可点 | **直接撤回**你那一步 —— 不用等对方点头。对方的着法还没建立在这一步上，撤掉它不影响任何人 |
| **B. 对方已经回应** | 可点 | 发**申请** → 对方在右侧浮层里「同意 / 反对」（**30 秒**不回应自动拒绝）→ 同意后撤**两步**（对方的应手 + 你那一步）、**轮到你重走** |
| **C. 你一步都没走过** | 置灰 | 没有可悔的 |

1. **B 里为什么必须撤两步**：对方的应手是踩在你那一步上算出来的，单独撤掉你自己那一步在规则上无解（轮次也对不上）。撤掉两步，轮次正好回到你 —— 还是「轮到你重走」。
2. **棋钟不回退**（沿用 2026-11-10 的拍板）：时间照常走，悔棋者重新开始计时 —— A 里对方思考的那段时间算**对方**的，不转嫁给你。
3. **终局也能悔**（2026-11-20）：自己那一步把对方将死 / 逼和了，照样能撤回 —— 终局状态里也有「悔棋」按钮。但**只有「棋盘规则」判出来的终局才悔得动**：认输 / 双方同意和棋 / 超时判负 / 弃权都是**人做出来的决定**，撤一步棋改不了它。
4. **服务端权威**：悔棋走的是 chess.js 活实例的 `undo()`，三次重复的计数、吃路兵目标格、50 回合计数都跟着一起退回去。

对电脑下棋时**不摆和棋和悔棋** —— 电脑是对手，它没有「同意 / 反对」这个交互（悔棋它只会秒同意、求和它只会拒绝，都别扭）。人机局的 HUD 只有「认输 + **撤回**」两个按钮。

### 人机局的「撤回」

人机对弈时对着电脑悔棋没意义（电脑不跟你商量），所以人机局把「提议和棋 / 悔棋」换成**一个「撤回」**（用户 2026-11-12 拍板）。规则：

1. **一次撤回 = 回到上一次轮到玩家走子的局面** —— 玩家那手**连同 AI 的应手**一起撤掉。只撤玩家那手在棋谱栈上留不下：AI 的应手是踩在玩家那步上算出来的，少了前一步它就不存在了。玩家看到的效果是「我的棋子回到原位」。
2. **可以连点**，一路撤回到开局：玩家的手全撤完之后**再撤一次**，把 AI 的开局也撤掉，回到初始局面，AI 会重新走第一步（撤回到 0 手的那一瞬间局面会停一下，等 AI 重新落子）。
3. **棋钟不回退**（和「悔棋」同一条规矩）：时间照走，撤回者重新开始计时。
4. **服务端权威**：撤回走的是 chess.js 活实例的 `undo()`，三次重复的计数、吃路兵目标格、50 回合计数都跟着一起退回去；撤回后和棋 / 悔棋 / 再来一局的临时状态一并清空。
5. **电脑正在想的时候点撤回**，那一手会**作废** —— 局面已经变了，它算出来的那一手不再成立（否则那一手会落在撤回之后的局面上）。

### 对局页的布局

对局页**没有侧栏**，整行宽度全让给棋盘。棋盘（2D）是**正方形**，屏幕上总有一边是空的 —— 页面据此自动选排法：

| 屏幕形状 | 排法 | HUD | 聊天 |
| --- | --- | --- | --- |
| **宽**（视口宽 > 高） | 三列并排 | 棋盘**左边** | 棋盘**右边** |
| **窄**（视口宽 ≤ 高，**含正方形视口**） | 三行堆叠 | 棋盘**上面** | 棋盘**下面** |

两种排法**共用同一份页面结构**，只是 CSS grid 的行列不同 —— 页面里没有任何绝对定位的面板，所以**结构上就不可能压住棋盘**。

判定规则（三条，依次判断，见 `planStageLayout`）：

1. 视口宽 ≤ 高 → 走**窄屏**（正方形视口算窄屏，好把棋盘的长宽都缩小、把上下都让出来）；
2. 左右两列摆不下（2D 中间列不足 440px / 3D 不足 620px）→ 走窄屏；
3. 左右分列算出来的棋盘**比堆叠还小或一样大** → 也走窄屏（分列必须换来更大的棋盘，否则不划算）。

判定用的是**视口**宽高，不是页面内容区宽度 —— 页面有左右 padding，用内容区判会失准。

对局页里的常驻块：

| 块 | 内容 | 宽屏 | 窄屏 |
| --- | --- | --- | --- |
| **HUD** | 对局状态、双方名字、剩余时间、认输 / 提议和棋 / 悔棋（人机局则是认输 / 撤回）/（终局时）各自那一行的「再来一局」/（终局后）「复盘」与它的 还原 / 上一步 / 下一步 / **悔棋**（终局也能悔棋） | 竖排在**左列** | 横排一条，在棋盘**上方** |

玩家名字太长时**自动截断成省略号**（宽屏截在左列里，窄屏截在视口里），名字不会把 HUD 撑宽、也不会把页面撑出横向滚动条。
| **聊天块** | 聊天记录 + 输入框 + 发送 | 在**右列**，记录区与棋盘等高 | 只留「💬 聊天」按钮，**记录/输入框/发送在弹窗里** |
| **快捷聊天** | 6 个快捷短语 | 聊天块下方 3×2 | 和「💬 聊天」按钮并排**一行**（放不下就横向滚动） |

点一下快捷聊天直接发一句，对方屏幕上飘一条弹幕（**不进聊天记录**）。

### 设置（顶栏齿轮）

顶栏右侧有一个 **⚙ 齿轮** 按钮，点开是设置弹窗。设置存在浏览器 **localStorage** 里（跟着「这个人 / 这台设备」走，换设备回默认）。

| 设置项 | 说明 |
| --- | --- |
| **音效** | 开关 + 音量滑块。**默认关**（要自己打开）；落子、吃子、将军、终局各有不同的合成音 |
| **棋盘外观** | 5 套配色：**原木（纯色）** / **蓝白** / **绿白** / **灰白** / 胡桃木纹 |
| **棋子风格** | 4 选 1：**经典** / **卡通** / **像素** / **涂鸦**（改的是**造型**） |
| **棋子材质** | 3 选 1：**木质** / **金属** / **塑料**（改的是**表面**） |
| **辅助下棋** | 打开后，轮到你走时棋盘上会出现一根**蓝色指引箭头**，指向引擎推荐的下一着 |
| **翻转棋盘** | 手动把棋盘转 180°（默认仍按你的执子颜色朝向） |

**音效是现场合成的**（WebAudio），仓库里**没有一个音频文件**：落子/吃子是带通噪声 + 低频共鸣，将军是两声短鸣，胜负是三音琶音。浏览器要求音频上下文必须在用户手势里解锁，所以第一次打开音效开关时才会真正出声。

**棋盘默认是纯色方块**。早先的棋盘是「木纹贴图 + 底色」叠出来的，格子看上去不是纯色，深浅还会随纹理起伏 —— 远近两排的明暗差异容易让人把深浅格看串。所以默认改成纯色块，木纹降级成一个**可选主题**。

### 棋子外观（风格 × 材质）

设置里有两个**互不干扰**的切换项，各自带一枚**真实的棋子缩略图**预览：

- **棋子风格**（4 选 1）改的是**造型** —— 棋子长什么样；
- **棋子材质**（3 选 1）改的是**表面** —— 棋子是什么质感。

两条轴**正交**，所以有 **4 × 3 = 12 种组合**（不是 6 个互斥选项）。2D 与 3D 两个视角都会跟着变。

| 风格 | 造型上做了什么 |
| --- | --- |
| **经典**（默认） | 传统车床造型：底座、腰身、球头。描边 2.6，48px 的棋盘上也看得清结构 |
| **卡通** | 圆胖团子身 + **大白眼**（眼白/瞳孔/腮红），轮廓用「两遍画法」撑出一圈干净的粗墨线 |
| **像素** | **32×32 位图 + 专属造型语言**：方块边缘硬切不糊。**不**是从经典造型降采样得来的（降采样会把象的顶珠、后的冠尖全磨没，六子会撞成一样）—— 而是自己一套造型：王是粗十字、后是中央大尖+两侧翼、车是三个方垛、象是歪顶主教冠、马是横向侧脸、兵是圆球头 |
| **涂鸦** | 经典骨架 + **空间平滑噪声**抖动（按坐标抖，不按序号 —— 按序号会把王冠抖成锯毛）+ 斜线排线 + 斗鸡眼 |

| 材质 | 表面上做了什么 |
| --- | --- |
| **木质**（默认） | 哑光底色 + 顺着走势的木纹细线 |
| **金属** | 冷灰底色 + 一道**斜切硬边高光带**（金属的招牌）+ 底部暗面 |
| **塑料** | 冷白底色 + **柔和圆斑**高光（塑料的高光是软的，金属是硬的）+ 底部环境反光 |

两条贯穿全部风格的规矩：

- **描边反着配**：白方用深描边、黑方用浅描边 —— 浅格和深格上都读得出轮廓；
- **材质不会溢出**：木纹/高光先画一大片，再用 `clipPath` **裁回棋子轮廓内**，所以棋盘上不会出现棋子的影子以外的色块。

素材全部**代码生成**（`scripts/generate-pieces.ts` 直接渲染 `PieceGlyph` 本体产出 SVG），仓库里**没有一张第三方图片**。

**像素风的辨识度是有门禁的**（`tests/pixel-silhouette.test.ts`，7 条）：

- 六子的剪影缩到 **56px**（棋盘上棋子实际渲染 70px，判据取更小的值 = 更严）后，**任意两枚的 IoU ≤ 60%**。
  这一条是踩过坑才有的：最初像素版是「把经典造型降采样成 32×32」，结果象的顶珠只剩 1 格、后的五尖冠被切成离散单像素，
  而六子的下半部分一模一样 —— 缩到实际尺寸后**王 vs 后 的 IoU 高达 73.7%**，肉眼就是「都长一样」。
  而且把分辨率提到 48×48 **只会更糟**（73.6% → 81.9%）：分辨率越高，六子共用的「柱体 + 底座」保真度越高，越像。
- 加上体量分档、特征结构规格（段数 / 最宽段）、象的斜顶必须真的歪、高矮次序等判据 —— 因为 IoU 是单一维度，
  局部特征退化（垛缝消失、横杠被削窄）它看不见。
- `npm run mutate:pixel` 每次改造型都会跑一遍：**把造型改回 bug，门禁必须变红**（6/6 全部抓到）。

### 棋谱（记谱卡）

快捷聊天那一行的**右边**有一个 **♟ 棋谱** 按钮（按钮上带已走步数）。

- **宽屏**：棋谱是**左栏常驻的一张记谱卡**（HUD 卡的下面），**不是弹窗** ——
  棋谱是要「边下边看」的参照信息，做成弹窗就会压暗整页、盖住右边的聊天，
  还会挡住棋盘（用户原话：「是不是就不适合做成弹窗」）。记谱卡在文档流里，棋盘一点不受影响，
  高度锁到和棋盘同一档，着法多了在卡里自己滚。点「♟ 棋谱」按钮是**收起 / 展开**这张卡。
- **窄屏**：左栏变成顶部一整条，常驻卡会把棋盘挤没 → 窄屏走**底部浮层**（跟聊天弹层同一套：同样的底色 / 边框 / 圆角 / 阴影 / 头部）。

两种形态里着法都一样：

- 着法按「回合号 · 白着 · 黑着」逐行排列（服务端记的是 chess.js 生成的标准 SAN：`Nf3`、`exd5`、`O-O`、`e8=Q`、`Qh4#`）；
- 底部有 **「复制 PGN」** —— PGN 是国际象棋界通用的棋谱格式，粘进任何棋谱软件都能读；
- 棋谱只给自己看，不影响对手。

**「复制 PGN」在局域网 http 页面上照样能用**：局域网上跑的是 `http://192.168.x.x`，
那**不是安全上下文**，浏览器不提供 `navigator.clipboard`（直接调会抛异常，就是以前那句
「复制失败，请检查浏览器权限」）。所以复制走 `src/lib/clipboard.ts` 的 `copyText()`：
先用现代 API，不可用就落到「临时 textarea + `execCommand('copy')`」那条老路上。

### 复盘（终局之后）

一方获胜（或和棋）之后，**双方**各自的 HUD 操作区都会出现一个 **「复盘」** 按钮。
点开它，**HUD 操作区**就变成一组控制器：

| 按钮 | 作用 |
| --- | --- |
| **还原** | 没自由走棋时回到**开局**；自由走棋之后回到**自由走棋之前**的那个棋盘 |
| **上一步** | 沿棋谱往回走一手 |
| **下一步** | 沿棋谱往前走一手 |

**复盘是各看各的**：它完全在本机算，一条报文都不发 ——
谁点了复盘，谁的棋盘就走自己的进度；对方没点复盘，棋盘还停在终局局面。
两个人都点了复盘，两边各退各的，互不干涉。

**复盘里还能自己走棋** —— 而且**双方的棋子都能动**（不用管轮到谁），
这是探索局面的地方，不是下棋。下完这一步之后：

- **上一步 / 下一步会藏起来**（沙盒里的局面不在棋谱上，
  让「下一步」接着走棋谱会让棋盘硬跳一手，跳得没有道理）；
- 只剩 **「还原」** 能出去 —— 点了它回到自由走棋之前，步进键才重新出现。

> 棋盘正中那张终局结果卡（黑方胜利 · 将死）在**复盘时会让位**，
> 好让你看清棋盘。退出复盘它就回来。

### 教学练习（/practice）

大厅里「开始一局」卡片**下面**有一条独立入口：**教学练习**。

它**不是**第五种开局方式 —— 那四枚按钮点开的是「开一局棋」的表单，
而教学练习是**另一个页面**（看开局课 / 自己摆残局），所以单独一行放。
进去之后顶部两枚按钮切换两个分区。

#### 教学

左侧是**课程列表**，上方一行**分类筛选**（全部 / 基本功 / 开局 / 应对 / 残局，
每个按钮上带该类课数 —— 三十二课平铺一列太长）。

课分四类：

| 分类 | 讲什么 |
| --- | --- |
| **基本功** | 开局四原则；战术：叉子 / 双将与闪击 |
| **开局** | 白方与黑方各自的开局体系：伦敦 / 意大利 / 西西里·纳道尔夫 / 后翼弃兵·正统 / 王翼弃兵·费舍尔 / 西班牙 / 法国·维纳瓦尔 / 卡罗康 / 苏格兰 / 维也纳 / 尼姆佐-印度 / 格林霍姆 / 王印度 / 后印度 / 荷兰 |
| **应对** | **对方开了这个开局，我该怎么接**（见下） |
| **残局** | 车兵与底线；对王与关键格 |

选一课，中间是棋盘，右侧是讲解：

| 控件 | 作用 |
| --- | --- |
| **上一步 / 下一步** | 沿演示线前后走一手（棋盘局面跟着变，并画出「上一步」箭头） |
| **重来** | 回到开局局面 |
| **走法演示 / 典型摆法** | 前者看演示线，后者看**这一课推荐怎么摆** |
| **线路切换** | 应对课有 2~3 条线路时出现（见下） |

**「典型摆法」是这一页的重点**：伦敦那课会直接把
「兵 d4/e3/c3、马 f3/d2、象 f4/d3」摆到棋盘上，并逐条说明每个子为什么在那儿 ——
这就是「教你如何摆伦敦开局」的那一半。

每一课的内容都是**着法 + 讲解**，而且局面是**由着法推导**出来的（不是手写 FEN）：
讲解说「车到第七横线」，棋盘上就一定真的是车在第七横线；
每一手都经 chess.js 复核（`tests/practice.test.ts` 里逐课**每条线路**真走一遍）。

**课程行上的空心圈 / 实心圈**是**侧别**：空心圈 = 白方那侧的课，实心圈 = 黑方那侧的课。
「应对」类课程讲的是「站在对手的对面」，所以侧别是必填项 —— 不用看字就知道这课是给哪一方准备的。

##### 应对课：一课多线路

只教「某个开局怎么走」是不够的 —— 真正用得上的是**对方走了那个开局之后我方怎么接**。
应对课讲的就是这个，而**对方往往有几条正经应手**，所以一课里有 3 条线路可切：

| 课 | 三条线路 |
| --- | --- |
| 对付后翼弃兵 | 斯拉夫 / 半斯拉夫 / 接受变例 |
| 对付意大利开局 | 吉奥科·皮亚诺 / 四马开局 / 弃子陷阱 |
| 对付西班牙开局 | 柏林防御 / 交换变 / Breyer |
| 对付卡罗康 | 交换变 / 经典变 / 潘诺夫攻击 |
| 对付法国开局 | 交换变 / 斯泰因茨 / 塔拉什 |
| 对付西西里 | 陶氏防御 / 尼姆佐维奇 / 四马开局 |
| 对付尼姆佐-印度 | Sämisch / 机器人防御 / 经典体系 |
| 对付伦敦开局 | 常规应对 / 反伦敦（…g6）/ …c5 应法 |
| 对付王翼弃兵 | 古典应法 / Falkbeer 反弃兵 / Muzio 弃子 |
| 对付格林霍姆 | 主变 / 交换变 / 大括号变 |
| 对付王印度 | Sämisch 体系 / 古典体系 / 阿维尔巴赫 |

切线路 = 换一整条演示线：棋盘局面、逐步讲解、要点清单整套换掉，
所以能看出「这三条路各自什么性格、什么时候选哪条」，而不是背三份互不相干的谱。

#### 自由练习

不限时，自己扮演双方对弈：

1. **摆棋**：左侧调色板选子（白方 6 枚 / 黑方 6 枚 / 橡皮），点棋盘格子落子或拿走；
   「清空」「初始摆法」「翻转」三个工具；「先走方」决定谁先走。
2. **开始练习**：摆法先过一遍校验（**双方各恰好一个王**、兵不能站在第一 / 第八排），
   不合法就在按钮下面说清楚错在哪（**常驻字段旁**，不是飘走的 toast）。
3. **对弈**：棋盘上**双方的棋子都能动**（与「复盘 · 自由走棋」同一套语义），
   走完一步就轮到对方；左侧是棋谱，右侧是「轮到谁 / 几手 / 视角」。
4. **上一步 / 下一步**（2026-11-20）：走错了不用重开 —— 退回去改一步再继续下。
   - 「上一步」退一手（可连点，一路退回开局），「下一步」进一手；
   - 棋盘显示的局面由「起始局面 + 棋谱 + 游标」**算出来**，棋谱里**当前那一手会被标出来**；
   - 在中间位置落新的一手 → **后面的旧着法作废**（换了一条线，跟棋谱编辑器一个道理）；
   - 右侧的「手数」读数是「当前位置 / 总手数」。
5. **棋盘和对局页一样大**（2026-11-20）：练习页改用**宽容器**（和对局页同一套），
   棋盘从约 358px 变成约 700px —— 之前挤在窄容器的中列里，走起来很难受。

> 自由练习是**纯本机**的：不连服务端、不占房间、不限时 ——
> 它只是把「摆法」变成一盘双方都由你下的棋。

#### 残局关卡

**做题**，不是看讲解：给你一个残局局面，你自己走，走对了才往下走。

左侧是**关卡列表**（30 关，按难度从易到难排），每关带编号、主题名、目标、难度星，
通关的会打勾（进度存在浏览器本地）。中间是棋盘，右侧是目标与操作。

| 控件 | 作用 |
| --- | --- |
| **走子** | 只走**你自己那一方**的子；对手的应手**自动接上** |
| **提示** | 点一下才画出这一关该走的那一步（蓝色指引箭头，和「辅助下棋」同一套几何） |
| **重来** | 这一关从头开始 |
| **翻转** | 翻转棋盘视角（玩家执黑时默认已经翻转） |

走错了：棋盘上**起止两格标红**，右边写「这一步不对」，**局面一步都不动** —— 可以直接再走。
走完整关：显示「通关」并出现「下一关」，同时给出这一关的**教学要点**（要点只在通关后出现 ——
提前印出来就把题做完了）。

##### 题目从哪来

题库来自 **Lichess 开放题库（CC0）**，由 `npm run gen:endgame-puzzles` 生成：
从题库里挑出**真正的残局**（非王棋子 ≤ 7 枚），再用 Stockfish 逐关复算 ——
确认引擎的最佳着法就是题库的解、确认目标与局面一致、算出每个节点上**哪些着法也算走对**。

**运行时完全不依赖引擎**：每一关把走通的着法线固化在 `src/lib/practice/puzzles/data.ts` 里，
判定纯靠 chess.js 走线 —— 浏览器零延迟、难度可复现（同一关永远是同一道题）。

关卡的**难度按人类评分分档**（Lichess 的 Glicko-2 评分，是几百万玩家实际做题成绩算出来的）：
1 档 < 1100 / 2 档 1100~1500 / 3 档 1500~1900 / 4 档 1900~2300 / 5 档 ≥ 2300。
杀棋题再取一个下限 —— 一道 5 手杀的题不管评分多少，都不该被标成「入门」。

> 引擎层为此补了一处能力：UCI 的 `score mate N` 以前被直接丢掉
> （杀棋局面的 `score cp` 是 null，「一步杀」和「十手杀」在分值上长得一模一样），
> 现在 `mateIn` 会一路透出到 `AnalyzeResult` —— 残局关卡按「几步杀」分档靠的就是它。

### 辅助下棋（提示按钮 + 蓝色指引箭头）

设置里打开「辅助下棋」后，**HUD 的操作区最后面会多一个「提示」按钮**（认输 / 提议和棋 / 悔棋 之后；人机局则是认输 / 撤回 之后）。
**点了它才会显示下一步怎么走** —— 不会自动弹出来。

| 状态 | 「提示」按钮 | 棋盘上的蓝色箭头 |
| --- | --- | --- |
| 没打开辅助下棋 | **不显示** | 没有 |
| 打开了，但还没点 | 显示（轮到你时可点） | 没有 |
| 点了「提示」，正在算 | 显示「思考中…」（禁用） | 算完才出现 |
| 箭头已经显示着 | 显示「收起提示」 | 有；再点一次收起 |
| 局面变了 / 轮不到你走 | 按钮置灰 | 自动收起 |

- 服务端用**和 AI 同一套引擎**算（不限强，要最强的那一档）；
- 结果**只发给请求者本人**（提示是私人的，不广播 —— 对手看不见你的推荐）；
- 棋盘上画一根**蓝色指引箭头**，几何与「上一步走子箭头」完全一致，只是换了颜色，两者同时出现也不会看混；
- 观战者没有「提示」按钮（服务端也只给「轮到你」的人算）。

### AI 难度

人机对弈面板里有 **「难度」** 下拉框，三档（自绘下拉，不是浏览器原生控件）：

| 档位 | 说明 |
| --- | --- |
| **简单** | 搜索浅、速度快，适合刚学规则 |
| **普通** | 默认档，深度与时间居中 |

### 聊天记录：平时一行，要看才弹窗

聊天记录**按屏幕宽窄分两种形态**，两种都不会「挤成一团看不了」：

| | 宽屏（左右分列） | 窄屏（含正方形） |
| --- | --- | --- |
| 平时看到什么 | 右列那个 300×525 的大框，**记录常驻**，每条消息**换行完整显示** | **只有一行**：「💬 聊天」按钮 + 6 个快捷聊天 |
| 想看全部时 | 不用点，一直都在 | 点「💬 聊天」→ **弹出一个大框**：历史聊天（可滚动、每条换行完整显示）+ 输入框 + 发送按钮 |
| 收起 | —— | 点「收起」/ 点框外 / 按 Esc |
| 有新消息 | 记录一直看得见，不用提醒 | 「聊天」按钮**右上角出角标**（未读条数，>99 显示 `99+`） |

窄屏下面那条只有一行高，历史聊天、输入框、发送按钮**平时根本不显示** —— 塞进去只会被挤成两行、长消息还会被截成省略号，实际验收下来「完全看不了」。所以全部收进点「聊天」才弹出的浮层里。

角标只数**对方**发来的消息（自己发的当然看过）、只在**窄屏**、且**弹窗没打开**时计数；打开弹窗即清零。宽屏记录本来就常驻可见，不需要提醒。

宽屏那个常驻的记录框**有高度上限**：聊天内容变多时，多出来的部分在**记录区内部滚动**，整页**不会出现纵向滚动条**（以前记录区没有上限，内容一路把右列 → 网格行 → 整页顶高，页面就多出一条滚动条）。

> 实现上的一个坑：记录区是纵向 flex 容器，**不能用 `justify-content: flex-end`** —— 它会把超出的内容整体往**上**推，溢出落在内容盒的起始边，那部分内容既被裁掉又**滚不到**（`scrollHeight` 都不增长）。正确做法是 `justify-content: flex-start` + 首项 `margin-top: auto`：有富余空间时消息仍然贴着底部，内容超出时溢出方向朝下，可以正常滚动。

弹层是**主动点击才出现**的临时浮层，展开时会盖住一部分棋盘；这和「常驻面板一律不压棋盘」那条规矩不冲突 —— 那条管的是常驻元素。

贴在棋盘上方的这几块（窄屏的 HUD 与聊天块）**一律不带投影**：它们的层级高于画布，一旦有投影，投影就会直接糊在棋盘顶边（3D 画布上沿会被压暗，2D 棋盘顶边会发暗）。层次靠边框和底色区分，不靠投影。窄屏时 HUD 与棋盘之间还留了 12px 间距。

**走子箭头**：从棋子**原来**的格子指向**现在**的格子，一根箭头同时说明「谁走的」和「走到哪」；起点和终点的格子都会亮一下琥珀色。2D 是画在格子上的一枚扁平箭头，3D 是贴棋面的立体箭头（挤出了厚度，斜视角下有体积感）。

### 棋钟

可选时限：不限时 / 5 分钟 / 10 分钟 / 15 分钟 + 10 秒 / 30 分钟（快速匹配还多一个「任意」）。
棋钟由服务端计时，刷新页面不丢。

**时限是房间的属性**：建房时定下，这一局全程不变 —— 所以「加入房间」时不用再选时间，
选了也没用（房主定的时间说了算）。

### 超时判负，但这局还能继续下

超时**不是终局** —— 它只是**判负**：

- 计时一越界，就弹一条 toast 写明「对手超时，判你胜」之类的话，**结果就此锁定**；
- 但对局**不结束**：双方照样能走棋，认输 / 求和 / 悔棋都照常用；
- 棋钟**继续走**，而且允许变成**负数**（`-1:23` = 已经超时 1 分 23 秒），显示为红色；
- 超时方那一行标一个「**已超时**」；
- 因为结果已定，**「再来一局」照常能申请**，双方同意就开新局。

> 这一局**还在下**，所以棋盘正中那张**终局结果卡不出现** ——
> 它是浮在棋盘正中、盖住半张棋盘的，这局还没结束，不能拿它挡住正在下的棋。
> 超时的信息由**超时方那一行的「已超时」标记**加上超时那一刻的 toast 交代。

**结果锁定的含义**：超时那一刻定的结果，之后**不再改写** ——
哪怕后来真的走出将死、或者有人认输，那一行的「已超时」标记仍然挂着。
超时是「已经判负了」，棋是「还想下就继续下」。

判负之后**增量照发**（规则统一，不给判负方开特例）：判负方走一步仍拿得到那几秒增量，
所以它的钟**有可能被拉回正数** —— 这时「已超时」标记就是唯一还亮着的那个信号。

### 刷新页面

刷新后**身份与座位保留**（token 存在 sessionStorage），棋钟、走子记录、聊天全部还在。

### 关掉网页再打开

**关掉标签页、关掉浏览器之后再打开，座位还是你的** —— 走的是「座位凭证」这条路：

- 服务端给每个座位发一把**只发给座位本人**的凭证（不广播，对手拿不到）；
- 客户端把它存进 `localStorage`，**按房间码**存 —— 关标签页、关浏览器都还在；
- 重开后打开 `/room/<房间码>`，客户端自动用记住的用户名登录，再凭凭证**认领回原来那个座位**（颜色、准备状态、走子记录、棋钟全保留）；
- 认领要求**原主人已断线** —— 对方还连着的时候，凭证抢不走那个座位。

认领成功后，旧身份的会话档案会被清掉 —— 否则他再连回来会以为「我还在这个房间里」，
而座位已经换人了（两处都以为自己是棋手，座位只有一个）。

### 掉线与离开

| 情况 | 结果 |
| --- | --- |
| 点「离开」 | 立即判对方胜，房间结束 |
| 关页面 / 断网 / 设备休眠 | 对方看到「掉线中…」，**5 分钟**内回来可以接着下；超时判对方胜 |
| 断网后网络恢复 | 客户端**自己**察觉并重连（顶栏显示「重连中…」），座位和身份都不变，不用刷新页面 |
| **双方都掉线** | 僵死座位被清掉，房间回落成「等待对手」；房间里再没有任何在线的人时，房间会被清理并从大厅列表移除 |

**宽限期为什么是 5 分钟**：浏览器对「断网」的感知很慢 —— 拔网线、切 Wi-Fi、手机息屏之后，
WebSocket 的 close 事件可能几十秒后才触发，服务端还要再等 45 秒心跳超时。
从「真的断了」到「服务端判负」可能超过 100 秒，60 秒的宽限期根本不够覆盖
「切 Wi-Fi / 进电梯 / 短暂断网」这些常见情形。代价是僵尸房间会在大厅多挂 5 分钟
（显示为「等待重连」而不是「进行中」）。

**断网重连靠客户端心跳**：客户端每 5 秒发一次 ping，**10 秒收不到任何服务端消息**就认定连接已死，
主动换一条新连接重连 —— 把「断网 → 重新连上」压到 10 秒以内。
半开连接（网络断了但 TCP 没断）下浏览器的 close 事件可能永远不来，
所以客户端**不等那个事件**，自己摘掉旧连接、自己重连。

#### 「离开」具体怎么走

| 你的身份 | 对局状态 | 点了「离开」 |
| --- | --- | --- |
| 棋手 | 进行中 | **先弹二次确认**（离开=判你输）→ 确认后：服务端摘掉你的座位、对局判负结束、你回到大厅 |
| 棋手 | 等待对手 / 已结束 | 直接离开，回到大厅 |
| 观战者 | 任何状态 | **直接离开**（观战离开不影响对局，没有要确认的理由） |

离开之后：

- 服务端**真的把座位收了** —— 对方那边看到的是「对局结束、对方判负」，不是一个空座位；
- **不会被迟到的房间快照弹回对局页** —— 回到大厅就稳稳待在大厅；
- **不会被自动拉回房间** —— 「离开」之后页面不会再自动把你加进这个房间。

服务端每 15 秒发一次心跳，超过 45 秒没有任何回音就主动断开该连接——所以设备休眠造成的「假在线」不会让房间永远挂着。

大厅里的房间卡会跟着服务端状态实时刷新：

- `进行中` —— 座位上还有人
- `等待重连` —— 对局还在，但两边都没人在（宽限期内等人回来）
- `等待对手` —— 房间还在，等新玩家入座
- `已结束` —— 对局已有结果

### 在线名单与私信

顶栏右上角那枚「在线 N」**能点**：点开就是**在线的人名单**。
**大厅页和对局页都有这一套** —— 顶栏本来就是全局入口，进了棋盘也照样看得见谁在线。

| | |
| --- | --- |
| 名单里有什么 | 当前在线的人（**只算登录过的**；刚连上还没取名字的不算一个人） |
| 数字对不对 | 「在线 N」的 N **永远等于名单行数** —— 数字和名单对不上就是骗人 |
| 自己 | 自己那行标着「你」，**点不动**（不能给自己发私信） |
| 对别人 | **左键**点某个人 → 直接进他的私信；**右键**点某个人 → 菜单里选「发送消息」→ 私信面板直接落在**那个人**身上 |
| 浮层怎么收 | **点别处就收起** —— 名单是顶栏下拉出来的浮层，它的层级高过私信抽屉；开着它再去点「私信」，抽屉就在名单底下被盖着（看得见、点不着） |

私信**不经过房间**（两个人没在对局里也能聊），走一条独立的 `dm.send` 通道。

- **入口在顶栏**：一枚「私信」按钮（**聊天气泡**图标，不是信封），有未读时右上角出**角标**（未读条数，>99 显示 `99+`）。
- 名单里每一行**行尾还有一枚气泡按钮** —— 点一下就是给这个人发消息。
  界面不靠「右键某人 → …」这种提示句教用户，怎么发消息由图标说明。
- **收到私信会弹一条提示**（「xx 给你发来一条消息」），位置在**顶栏下方** —— 别压住顶栏的按钮和角标（压住了就等于「说有未读」却看不见，而且那几秒里按钮还点不动）。
- **私信是有记录的**，不是一次性弹窗：抽屉里能翻**会话列表**（我跟谁聊过、最后一条是什么），也能点进某个对话**接着聊**。
- 面板**大厅和对局页共用同一套** —— 在大厅被人发消息时，人可能正在棋盘上，两边都得能翻出来。
- **记录存在浏览器本地**（按身份分桶，最多 300 条）：刷新页面之后历史还在，未读角标也还在。

#### 私信不会被轰炸

私信每发一条，**对面**就会弹一条提示 —— 所以「按住那颗快捷短语连点」在私信里
能把对方顶栏糊成**一整列提示条**。四道闸：

| | 做什么 | 谁在管 |
| --- | --- | --- |
| **发送间隔** | 同一个人 **1.2 秒**最多发一条（消息和邀请共用一个桶） | **服务端**拒收第二条（客户端那层只是提示，规则在服务端）；客户端的按钮**同时变灰、按不动** |
| **互惠限流** | 连着发 **3 条**之后**必须等对方回一条**才能继续（消息和邀请共用一个额度） | **服务端**拒收第 4 条；客户端的按钮**变灰、按不动**，对方一回话就恢复 |
| **提示合并** | 同一个人的连续私信合并成一条：「xx 给你发来 3 条消息」 | 客户端 |
| **提示区封顶** | 右上角同时最多显示 **4 条**提示，**新的在上**，整列待在右上角不往下铺 | 客户端（CSS 再加一道高度上限兜底） |

客户端的冷却比服务端**多等 200ms**：服务端的计时从「收到」那刻起算，
比客户端「发出」那刻晚几十毫秒 —— 不多等这一点，边界上会出现「按钮刚亮就发 → 被拒」。

**冷却期间不多写一句提示**（用户拍板）：按钮灰了就是「现在发不了」，
再补一句「冷却 N 秒」是多此一举 —— 用户要的是「按不动」，不是「读一句话再知道按不动」。

#### 互惠限流：能不能继续说，取决于对方有没有理你

1.2 秒的间隔挡的是**手速**，挡不住**骚扰** —— 一个人只要愿意等，每隔 1.3 秒发一条，
就能把对面淹没（对面只要不回，他就一直能发）。所以还有第二道闸：

| | 做什么 |
| --- | --- |
| 我给某人连发 **3 条** | 第 4 条**发不出去**（服务端拒收；客户端的按钮变灰、按不动） |
| **对方回了我一条** | 我的额度**重置**，又能连发 3 条 |
| **对方也一样** | 他回了我之后，他自己也只能连发 3 条 —— **双向各算各的，门槛相同** |

也就是：**能不能继续说，取决于对方有没有理我**。一问一答能正常聊；单方面刷屏聊不下去。
消息和**房间邀请**共用这一个额度 —— 邀请在对方面板上也长得像一条私信，
分成两个桶就等于留了一条「文字被挡了就改发邀请」的绕路。

规则落在**服务端**：客户端那层只是把按钮变灰，改个协议就能绕过去的那种不算规则。
服务端还会把「我还能给谁发几条」**推给客户端**（`dm.state`）——
客户端**不自己数**（自己数会和服务端对不上，对不上的后果是「按钮一直灰着，怎么都发不出去」）。

两个细节：

- **服务端给发送方也回一份** —— 不然「我发了没有」全靠猜；发送方自己的那份还带着收件人名字（「我跟谁聊过」才显示得出来）。
- 面板开着的时候来了新消息，角标会**当场清掉** —— 人正看着它，就不该还挂着「没看」。

### 房间邀请与分享

想拉人下棋有两条路：**私聊里发一枚邀请**，或者**把房间链接复制出去**。

#### 私聊里的邀请

- 在房间里时，私聊面板底部会多出一枚 **「邀请来这局 · 房间码」**（不在房间里就没有这枚按钮）。
- 点它 → 对方（**在线**才能收到）私信里出现的是一张**可点的卡片**：房间码 + 「加入房间」。
- **点一下卡片就直接进这局** —— 不用抄房间码、不用回大厅。
- 邀请不是一句话，是一条带房间码的结构化消息（`kind: 'invite'`），所以服务端认得出来 —— **私信面板里那条白名单**（只能发预设短语）管不着它。
- 服务端会把关，**发不出去**的情况：不在这个房间里 / 只是观战者 / 人机对局 / 房间已结束 / 对方不在线。
- **已在另一局里**点邀请 → 先弹一次**二次确认**（「离开当前对局（会判你输）并加入 XXXX？」）。离开一局就是判负，这条代价必须先摆在眼前，不能让一条邀请悄悄把人家正在下的棋判掉。

#### 分享房间链接

- 对局页顶栏有一枚**分享**按钮，弹一个小菜单：**复制房间链接** / **复制房间码**。
- 别人打开链接：
  - **浏览器记得用户名** → 直接进这局（能入座就入座，满了就观战）；
  - **不记得用户名** → 出现一张「取个名字，进这局」的卡片，填完**直接落到房间里**，不用回大厅。
- 链接长这样：`http://<局域网地址>/room/<4 位房间码>`。

两处一致：

- 分享与邀请**只给真人对局的双方**（观战者看不到房间码，人机局也没有「一起下」这回事）。
- 复制走的是 `navigator.clipboard`，**带老办法兜底** —— 局域网里跑的是 `http://192.168.x.x`，那不是安全上下文，`navigator.clipboard` 在那儿可能压根不存在。

### 5.1 验收规矩：三级，而不是每次全跑

**为什么改**：以前「验收」= 全量跑一遍（门禁 + 变异）。实测**整整 1 小时**，而且每加一个功能就多 2~3 条门禁 + 等量变异 —— 照这么下去以后真的要跑一整天。全量是**发版前**的动作，不该是**每次提交**的动作。

**现在**：验收分三级，**默认只跑跟你这次改动有关的那一级**。

| 级别 | 什么时候跑 | 跑什么 | 实测耗时 |
| --- | --- | --- | --- |
| **L0 提交前** | 每改完一处代码 | `npm run typecheck` ＋ `npm run test` ＋ **受影响组**的门禁与变异 | 15 秒 ~ 1 分钟 |
| **L1 功能完成** | 一个功能做完 | `npm run verify`（离线全量，26s）＋ **受影响套**的全部门禁（≤ 50s）＋ 受影响组的变异 | 2 ~ 8 分钟 |
| **L2 发版前** | 准备发布 | 上面全套 ＋ 所有套的全量门禁 ＋ 全量变异 | 约 40 分钟（arrow 那 40 条变异是大头） |

#### 怎么知道「受影响的组」

门禁按**机制**分成组（不按控件 —— 按控件分会让一条变异跨好几组）。改了什么机制，就跑那一组：

| 你改了 | 要跑的门禁组 |
| --- | --- |
| 聊天（记录 / 输入框 / 弹幕 / 快捷聊天） | `ui-style --group=chat` ＋ `arrow --group=chat` |
| 战利品（双方吃子） | `ui-style --group=capture` |
| 落子权 / 回合提示 | `ui-style --group=turn` |
| 宽窄屏布局、棋盘尺寸 | `ui-style --group=layout` ＋ `arrow --group=layout` |
| 走子箭头 | `arrow --group=arrow2d` ＋ `arrow --group=arrow3d` |
| HUD（按钮顺序、玩家行） | `arrow --group=hud` |
| 认输 → 再来一局 | `arrow --group=endgame` |
| 求和 / 悔棋 / 浮层 | `arrow --group=overlay` |
| 表单校验 / toast | `ui-style --group=notice` |
| **离开房间**（二次确认 / 座位释放 / 观战者离开） | `room-exit --group=player,spectator` |
| **在线名单 / 私信**（名单口径 / 左键与右键 / 收发 / 未读 / 图标尺寸 / 气泡图标 / 浮层收起 / 私信限频 / 提示区封顶） | `dm --group=list,message,topbar` |

#### 怎么跑

```bash
# 门禁：只跑相关的组（组名拼错会**直接报错退出**，不会静默全跑成假绿）
npx tsx scripts/verify-ui-style.ts   --group=chat,capture --url=http://127.0.0.1:3000
npx tsx scripts/verify-move-arrow.ts --group=chat            --url=http://127.0.0.1:3000
npx tsx scripts/verify-room-exit.ts   --group=player,spectator --url=http://127.0.0.1:3000
npx tsx scripts/verify-dm.ts          --group=list,message,topbar --url=http://127.0.0.1:3000
npx tsx scripts/verify-drag.ts        --group=drag2d,drag3d   --url=http://127.0.0.1:3000

# 变异：只跑某几条（每条变异只期望 1 条红，其余门禁在陪跑 —— 所以分组是省时间的大头）
npm run mutate:ui-style -- --filter=战利品
npm run mutate:arrow    -- --filter=弹幕
npm run mutate:room-exit -- --filter=观战者
npm run mutate:dm       -- --filter=未读
npm run mutate:drag     -- --filter=相机
```

#### 「按组强制」这条规矩

新功能**不要求**「每个门禁都配一条变异」—— 一个机制往往由好几条门禁从不同角度守着
（`G23` / `G23b` / `G23c` 都在守「认输要二次确认」），拆一条就红，代价很大。
真正要保证的是：

> **每个组（机制）至少有一条变异守着。**

执行点是变异脚本跑完时的**硬自检**（`checkGroupCoverage`）：哪个组一条变异都没有，
直接退出码非 0。这条自检用**全量变异表**判断，不是本次跑的子集 ——
「没跑到」和「没守着」是两回事。

#### 分组不是把门禁砍掉

跳过不属于本次分组的门禁时，它们**不计入结果、也不让退出码变成非 0**；
跑完会报告「本次跑了哪几组、跳过了哪几条」。所以：

- 选错组 → 看到「本次分组：xxx」，一眼就知道自己少测了；
- 组名拼错 → 直接报错退出，**不会**悄悄变成「全跑」而给你一份假绿。

## 6. 素材与开源合规

- **棋子**：自产。2D 用分层矢量路径（`src/components/PieceGlyph.tsx` + `src/components/pieceShapes.ts`），3D 用 Lathe / Extrude 程序化实体几何（`src/components/pieceGeometry.ts`）。同一份几何真源可导出静态 SVG 落到 `public/pieces/`。
- **棋子外观的两条轴**：**风格**（经典 / 卡通 / 像素 / 涂鸦）管造型，**材质**（木质 / 金属 / 塑料）管表面，正交两轴共 12 种组合。真源在 `src/lib/piece-appearance.ts`（枚举 + 调色板）与 `src/components/pieceShapes.ts`（造型）。
- **像素风是代码画的位图**：`src/components/pixelShapes.ts` 用矩形 / 梯形 / 圆盘 / 斜线**拼**出 32×32 的位图（不是手绘位图、不是降采样）。3D 像素棋子就是把这张位图**逐行挤成体素**，所以 2D / 3D 永远是同一套语言。
- **配色真源**：`piecePalette()`（`src/lib/piece-appearance.ts`）是 2D / 3D 棋子配色的**唯一来源**，白棋深边 / 黑棋浅边「反着配」；`public/pieces/**/*.svg` 由它导出，不会出现两套配色打架。
- **静态素材不手绘**：`scripts/generate-pieces.ts` **直接渲染 `PieceGlyph` 本体**产出 SVG —— 手绘一份、代码一份，迟早会漂移。
- **木纹**：程序化 Canvas 生成（`src/lib/woodTexture.ts`），2D / 3D 共用同一张贴图，风格统一且无版权问题。
- **字体**：系统字体栈，未内嵌任何商业字体。
- **配色**：全站亮色主题。文字对比度由 `npm run contrast` 门禁守着（WCAG AA，正文 ≥ 4.5:1，25 条逐条核），`npm run mutate:contrast` 再确认这个门禁本身不是假绿。
- **依赖**：除 `stockfish`（**GPL-3.0**，copyleft）外，全部为宽松开源许可（MIT / ISC / BSD / Apache-2.0 等）。`npm run licenses` 会遍历**整棵依赖树**审计许可证，发现非白名单许可即失败——它是**构建门禁**的一部分。因为 `stockfish` 是 copyleft，**本项目自身的许可也必须是 GPL-3.0**：门禁会同时校验「项目自身 license 与 copyleft 依赖兼容」，把它改回 MIT 会直接变红。
- **素材**：棋子 SVG / 3D 几何 / 木纹贴图 / 像素位图**全部由本仓库代码生成**（`scripts/generate-pieces.ts` 等），无任何第三方美术资源；字体走系统字体栈，未内嵌商业字体。

依赖调研与许可决策的完整记录见 `PLAN.md` 的「Q. 端侧模型调研 → 路线 A：接入 Stockfish 19」小节。

## 7. 已知限制

- 只支持局域网（无公网穿透、无账号体系），身份靠用户名 + 本地 token 区分
- 房间状态保存在 `.data/rooms.json`、会话档案在 `.data/sessions.json`（写入是节流的，**服务重启后未结束的对局会自动恢复**，玩家回来还认得回自己的座位；存档目录可用 `LAN_CHESS_DATA_DIR` 改）
- **房间状态在进程内存里** → 只能单实例，不能在后面挂 LB 复制多份；`.data` 只是落盘，多进程之间不共享
- **没有任何鉴权** → 放到公网上，拿到地址的人都能建房、开局、给别人发私信（详见 `docs/deploy.md`）
- 3D 需要支持 WebGL 的浏览器；WebGL 不可用时页面会提示
- 观战者不参与棋钟，聊天与走子实时可见
- **超时的结果是锁定的**：超时那一刻定的胜负，之后不会被将死 / 认输 / 和棋改写 —— 超时方那一行的「已超时」标记一直挂着。这是「超时即定局」的代价，但对局**不会**因此结束，双方想继续下就继续下
- **判负之后增量照发**：判负方走一步仍拿得到增量秒，所以它的棋钟**可能从负数爬回正数**；这时「已超时」标记是唯一还亮着的信号（时钟本身不再必然是红的）
- 断线后座位保留 **5 分钟**等重连，超时判对方胜；宽限期不可配置（写死在 `src/lib/constants.ts` 的 `DISCONNECT_GRACE_MS`）
- 「关掉网页再打开」靠浏览器 `localStorage` 里的座位凭证 → **无痕模式、换设备、换浏览器都会丢**（凭证没了就回不来了，只能观战）；宽限期也是 5 分钟，超时那个座位会被判负
- **旧格式存档（本功能上线前写的）会被自动迁移** —— 棋局状态（走子/棋钟/聊天）保住，文件顺手升级成新格式；但旧存档**没有座位凭证**，所以那种对局里座位主人关掉网页后未必认领得回座位
- 3D 是透视视角，棋盘在画面上天然被压扁（宽度接近满屏、高度约 57%）；想要更高的棋盘可以切到 2D
- **复盘只给对局双方**（观战者没有「复盘」按钮）；复盘是**探索用的沙盒** —— 没有三次重复 / 五十回合的判定，而且在沙盒里走一步会**丢掉吃过路兵的权利**（那枚兵不能再吃过路兵了）
- **超时判负的那一局没有「复盘」按钮** —— 超时**不是终局**（那局还在下），规则跟「终局结果卡不出现」一致；真到终局（将死 / 认输 / 和棋）才会出现
- 3D 转视角时**棋盘不再自动缩小**（用户明确要求），代价是转到斜角时棋盘上下边缘会有一部分走出画布 —— 棋盘是平铺的正方形，转到对角线方向时纵深变长、在画面里变高，而画布高度固定；想全程看得全就少转一点，或切到 2D
- 走子箭头只画**最近一步**（不画历史），这是为了避免棋盘上信息过多；要回顾整盘需要开第 4 节的观战视角或看服务端日志
- 私信记录只存在**自己浏览器本地**（按身份分桶，最多 300 条）：换一台设备看不到历史，服务端也不留底 —— 跨设备要能接着聊，得给私信加服务端存档

## 8. 许可证

本项目采用 **GPL-3.0**（完整条文见仓库根目录 `LICENSE`）。

**为什么是 GPL-3.0**：运行时依赖 `stockfish`（Stockfish 19 的 WASM 版）自身就是 **GPL-3.0**。GPL-3.0 的 copyleft 条款要求 —— 把 GPL 程序与本项目组合在一起分发时，整体必须同样以 GPL-3.0 分发。因此这不是"偏好"，是依赖树决定的硬约束。`npm run licenses` 门禁会同时校验「项目自身 license 与 copyleft 依赖兼容」，把 `package.json` 里的 license 改回 MIT 会直接变红。

引擎以**独立子进程**方式调用（`src/lib/engine/engine-source.ts`），未做任何修改。

**其余依赖全部宽松开源**：MIT / ISC / BSD-2-Clause / BSD-3-Clause / Apache-2.0 / 0BSD，外加 Next.js 自带的构建期数据集 `caniuse-lite`（CC-BY-4.0，署名即可，无 NC 限制）。**不存在任何私有协议、源码可见但非开源（BUSL / SSPL / Elastic）、或含非商业限制的依赖。**

**素材全部原创**：棋子 SVG、3D 几何、木纹贴图、像素位图均由本仓库代码生成；字体走系统字体栈，未内嵌商业字体。因此素材侧没有额外的第三方许可义务。

需要非 copyleft 许可（MIT / Apache-2.0）的话，唯一改动是**移除 npm `stockfish` 依赖**，改用系统安装的原生 Stockfish 或内置自研引擎 —— 见 `PLAN.md` 的「端侧模型调研」小节。
